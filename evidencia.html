1. Arquitectura general del sistema

La aplicación web sigue una arquitectura por capas con patrón MVC del lado del cliente. El navegador ejecuta Vistas, Controladores y Modelos en JavaScript; la persistencia, autenticación y seguridad por rol se delegan en Supabase, que expone PostgreSQL mediante una API REST (PostgREST) protegida con políticas RLS.

CLIENTE
① Capa de Presentación — Vistas
Archivos views/**.html + CSS. Formularios, tablas, modales y el panel de ayuda. Capturan la interacción del usuario y muestran los datos.
▼   eventos del DOM   ▲   render
CLIENTE
② Capa de Control — Controladores
controllers/*.controller.js. Escuchan eventos, validan y sanitizan entradas, orquestan la lógica y piden datos al Modelo. No acceden a la BD directamente.
▼   llamadas a funciones   ▲   objetos normalizados
CLIENTE
③ Capa de Modelo — Modelos
models/*.model.js. Único punto de acceso a datos: construyen las consultas, normalizan filas (_fromRow) y traducen errores (_msg).
▼   window.sb   ▲
PUENTE
④ Cliente de datos — supabase.client.js
Inicializa el SDK de Supabase (window.sb), gestiona el token de sesión (JWT) y helpers como miUsuarioId().
▼   HTTPS / REST + JWT   ▲
BACKEND
⑤ Supabase — PostgREST · Auth · RLS · PostgreSQL
Autenticación con JWT, API REST automática sobre las tablas y seguridad por rol mediante Row Level Security. Base de datos PostgreSQL (tablas eventos, noticias, oraciones, pqr, usuarios…).
Por qué esta arquitectura: separar Vista/Controlador/Modelo hace el código mantenible y testeable; delegar la seguridad en RLS garantiza que cada rol solo accede a lo que le corresponde aunque la validación del cliente fallara, porque la regla vive en la base de datos.

2. El patrón Modelo–Vista–Controlador aplicado

Todos los módulos comparten el mismo flujo. El usuario interactúa con la Vista; el Controlador reacciona, valida y coordina; el Modelo resuelve el acceso a datos contra Supabase y devuelve objetos limpios que el Controlador entrega a la Vista para renderizar.

🖥️ Vista

  • Formulario / tabla / modal en HTML
  • Dispara eventos (submit, click, input)
  • Muestra resultados y mensajes

🎛️ Controlador

  • Escucha el evento del DOM
  • Valida y sanitiza la entrada
  • Llama al Modelo y recibe la respuesta
  • Pinta la Vista / muestra alertas

📦 Modelo

  • Construye la consulta con window.sb
  • Normaliza filas (_fromRow)
  • Devuelve { ok, data, error }

④⑤ Datos: supabase.client.js → Supabase (PostgREST · Auth · RLS) → PostgreSQL

Responsabilidades (resumen)

CapaResponsabilidadQué NO hace

ControladorValidar, orquestar, conectar Vista y Modelo.No accede directamente a la base de datos.
ModeloAcceso a datos, normalización y manejo de errores.No manipula el DOM.

5. Grupo 9 — Ayuda

Caso particular de MVC: el Modelo es una base de conocimiento en memoria (no usa base de datos). El Controlador filtra ese contenido por rol y lo inyecta como un widget lateral en cualquier pantalla.

Nota de arquitectura: ayuda.controller.js no realiza ninguna llamada a Supabase. El "Modelo" es la constante BASE DE CONOCIMIENTO definida en el propio archivo, lo que hace la ayuda instantánea y disponible sin conexión.
